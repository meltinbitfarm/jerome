# Decisions

- D1: One project = one folder with the template repo cloned into it — projects are self-contained and easy to start. (refined by D17)
- D2: The user talks to the lead agent in plain Claude Code (terminal or VS Code), with no CLI/TUI of its own — don't duplicate what Claude Code already does well.
- D3: Subagents, not Agent Teams — Teams use several times as many tokens.
- D4: The lead agent passes file paths to subagents, not contents; subagents return a short summary and write the details to files — the lead agent's context grows slowly.
- D5: One model per agent: the large model only for the lead agent, Sonnet/Haiku for research and repetitive work — saves quota. (refined by D39: the model follows the kind of work, not the hierarchy)
- D6: Heartbeat: a scheduler launches headless `claude -p` with preconfigured permissions, an overlap lock and a budget per run — autonomous background work.
- D7: Narrative state in short markdown files (PROJECT.md, decisions.md, open.md), updated only by the lead agent — no conflicts, and sessions resume without rereading everything.
- D8: SQLite for events, logs and usage, written by hooks and scripts; the model queries it through bash scripts, not MCP — zero tokens to write, no fixed tool overhead.
- D9: The .db file is not versioned: numbered SQL migrations in the repo, DB created at setup, WAL mode — no binaries in git, updates without data loss. (refined by D51, D54)
- D10: (seed part revised by D53: no seed, prices in code) Seed only for reference data (states, event types, default budgets, model table); agent templates as markdown in templates/agents/ — agents and goals come from the briefing, not from rigid structures. (refined by D40: the catalog lives in the project-team skill)
- D11: Local read-only viewer, separate from execution: agent structure, messages, logs, reports, tokens, cost and estimated subscription % — if it breaks, the agents keep working.
- D12: Limits at two levels, per project and global (global DB in ~/.config/jerome/) — the subscription is one and shared across projects. (revised by D52: no global DB, global limits in `~/.config/jerome/account.json`)
- D13: Reporting: one log line per run, a periodic digest from the lead agent, a "decision request" when Fabio is needed — always know what was done.
- D14: Briefs in brief/v1 format with the project-brief skill; the source of truth is in the repo (.claude/skills/), with a copy uploaded to claude.ai — one briefing method everywhere. (refined by D26; by D34: the copy on claude.ai is optional)
- D15: (refined by D33: from the phone through the clipboard and `--from-file -`) Starting from the phone: brief saved in MementoVault and imported on the PC; starting from the PC: briefing in Claude Code with files written right away — starting from the phone is the typical case.
- D16: (superseded, see D18) The tool is called Odino; project marker `.odino` at the root — Fabio's choice, resolves Q1.
- D17: The template content lives in `template/` and the "new project" command copies only that folder; the project-brief skill has its canonical copy in `template/.claude/skills/`, linked from the root for development; project updates touch only the files listed in the manifest — Jérôme's development files never end up in projects, and updates never touch project state.
- D18: The tool is called Jérôme; `jerome` (lowercase, no accents) for the command, package, `.jerome` marker and paths — a French nod to Claude; Saint Jerome is the patron saint of translators, like the lead agent translating Fabio's ideas into tasks.
- D19: CLI as a Node package with the commands `jerome new`, `jerome view`, `jerome hook <event>`, installable with `npm i -g github:meltinbitfarm/jerome`; project hooks call the CLI instead of copied scripts; SQLite through the built-in `node:sqlite`, no native dependencies (requires Node ≥ 24, verified on 24.13.0); the package name is `@meltinbitfarm/jerome`, in package.json from now on and on npm if it is ever published (updated: meltinbitfarm scope and repo) — updating the package updates the hooks of every project without recopying scripts, and installing compiles nothing (V2).
- D20: Source of usage data: tokens per agent and per run read from Claude Code's JSONL transcripts, with hooks as the trigger (`agent_transcript_path` / `transcript_path`), lines deduplicated by `requestId` and cost estimated from the seed's model table; heartbeats run with `--output-format stream-json` and store the usage of the subscription windows (5 hours and 7 days) from the `rate_limit_event` in the global DB; global limits are expressed as % of these windows — hooks carry no tokens, and the only real subscription % is the one Claude Code exposes (see notes/usage-probe.md). (revised by D52: the % goes to account.json; by D53: usage keeps each field's largest value per requestId, since output_tokens grows across a response's lines)
- D21: Lean project profile: `jerome new` writes into the project's `.claude/settings.local.json`, which it adds to `.gitignore`, the keys that turn off installed plugins, synced ones included (`enabledPlugins` set to false), claude.ai connectors (`disableClaudeAiConnectors`), bundled skills (`disableBundledSkills`) and skills synced from claude.ai (`skillOverrides` set to "off", including the synced copy of project-brief: the project copy stays on, canonical per D14); any MCP server needed is added only in the project's `.mcp.json`; the profile names the plugins and skills installed on the machine, so it never goes in the versioned `.claude/settings.json`, where only machine-independent settings belong; the CLI manages only its own keys and leaves the others alone; `jerome doctor` moves profile entries it finds in `settings.json` to the local file, and rechecks the profile against what is installed and fixes it, including before every heartbeat; if it cannot, the heartbeat does not start, the block is logged and a "decision request" is opened (D13) — fixed startup cost goes from ~29k to ~12k tokens (notes/usage-probe.md §6), and the plugin list depends on the machine, so it has to be generated, not copied from the template. (updated: local settings instead of settings.json)
- D22: (superseded by D33) The import from MementoVault is done by the CLI with `jerome new <name> --from-vault <slug>`, without the model: it downloads the collection's `brief` document, checks `format: brief/v1` and sorts the sections into PROJECT.md, decisions.md and open.md following the "Import" table of brief-v1; it uses MementoVault's REST endpoint if one exists for reading a document, otherwise it calls the MCP endpoint directly over HTTP; the token lives in `~/.config/jerome/` (mode 600), never in the project; refines D15, and creating the three files initially does not conflict with D7 — import at zero model tokens, and no Memento MCP in the lean profile. (refined by D26: brief/v2, brief/v1 still accepted; refined by D31: MCP over HTTP, brief found by title)
- D23: The project status line calls `jerome statusline`, which writes the % of the 5-hour and 7-day windows to the global DB only when it changes from the last reading; it does not replace the personal status line: if one is configured, it calls it with the same input and appends its own part; it is the second source of the %, next to the heartbeats' `rate_limit_event` (D20) — interactive sessions update the % too, with no duplicate rows and without losing Fabio's status line. (revised by D52: written to account.json, not a global DB)
- D24: Everything versioned in Jérôme's repo is in English: documentation (README.md and docs/), CLI messages, code comments and the development files (decisions.md, open.md, PLAN.md, PROJECT.md, notes/), as well as commit messages; the only exception is brief.md, which stays in Italian as a snapshot of the starting point, with an English line at the top explaining it; Fabio keeps writing in Italian, and the agent records in English; updating the documentation is part of the definition of "done" for every phase, closed ones included — the repo is public, anyone who finds it understands what it does and how to use it, and the documentation never falls behind the code. (updated: development files, comments and commits in English too)
- D25: In projects, every subagent that changes something relevant appends one line to `docs/_pending.md` (date, agent, files touched, what changed in one sentence); a documentation agent on a cheap model (Haiku, D5) integrates it into the documentation, only on command: `/docs` in a session, `jerome docs` headless; integrated lines leave the queue; `jerome doctor` warns, without blocking, when the queue exceeds 20 lines — documentation gets updated without spending tokens on every task, and nothing gets lost in the meantime.
- D26: The project-brief skill is generic: instructions in English, and the briefing is held in the language the user writes in; brief format brief/v2 with fixed English section headings and IDs (Goal, Context, Constraints, Decisions…) and content in the user's language, while import still accepts brief/v1 with the Italian headings; storage is optional: inside a Jérôme project the project files, always; an external store when available, with MementoVault as the first adapter, described in a separate reference file loaded only when needed; otherwise the brief is shown as markdown to copy; no references to a specific person — anyone can use the template and the skill, the CLI can parse every brief without translating, and nobody pays tokens for a store they don't use. (refined by D33: no stores; D34: rules in `references/briefing.md`, shared with `jerome prompt`)
- D27: The agents in the template catalog (templates/agents/) declare `omitClaudeMd: true`, so they run as subagents without CLAUDE.md and the PROJECT.md it imports; built-in subagents still load CLAUDE.md, which tells them to ignore it — measured on a test project, a subagent call costs 2,518 input tokens with CLAUDE.md and 1,142 without, and those instructions are meant for the lead agent anyway.
- D28: `jerome doctor --json` is Jérôme's stable interface for external tools, such as claude-watch: one JSON object on standard output and nothing else, with `schema` (today `jerome.doctor/v1`), `ok`, `jerome` (CLI version), `mode`, `project`, `checks`, `profile`, `context` and `warnings`; the exit code always matches `ok` (0 true, 1 false, 2 wrong usage with nothing on standard output), and warnings never make `ok` false; check `id`s are stable, while `label` and `detail` are for humans; adding fields keeps v1, while renaming or removing a field, or changing its meaning, bumps the version; the human output can change freely; `--check` verifies and reports without writing anything, needed fixes go to `profile.pending` and make `ok` false, and external tools must call `jerome doctor --check --json` — they get a contract that does not break silently, instead of parsing the human output or Claude Code's `/context`, and checking a project never changes it.
- D29: Besides `--from-vault`, `jerome new <name> --from-file <path>` imports a brief from a file, and `-` reads it from standard input (so `pbpaste | jerome new <name> --from-file -` works); same validation and same mapping as `--from-vault`, done by the CLI without the model; the two options exclude each other; the folder name is the one given to `jerome new`, while the brief's `name` becomes the title in PROJECT.md; a brief with `status: draft` is imported with a warning; any `format` other than brief/v2 or brief/v1 stops the command before anything is created — with D26 the store is optional, and for anyone not using one this is the only way to bring a brief made on claude.ai into a project. (refined by D33: `--from-vault` is gone; D35: free text is accepted)
- D30: `jerome update [dir]` brings the template files of an existing project up to the installed version: it touches only the paths listed in the MANIFEST and never the state files (PROJECT.md, decisions.md, open.md, archive.md, brief.md, `.jerome`, `.claude/settings.local.json`), refusing them even if a MANIFEST listed them; it shows a diff per file and asks for confirmation before writing, `--check` shows the diff and writes nothing, `--yes` skips the question; `.jerome` becomes a JSON file with a schema version field, the Jérôme version and a hash of every template file as copied; a file whose hash matches the recorded one is updated, a file changed in the project is overwritten only after its own confirmation, and in projects created before this decision (empty `.jerome`) every file that differs from the template counts as changed in the project; paths dropped from the MANIFEST are reported, never deleted (refined by D38: removed when unchanged); `jerome doctor` adds a warning, not a failing check, when the template files differ from the installed version (skipped in Jérôme's own repository, where `template/` is the source and `jerome update` refuses to run, since an always-expected warning teaches to ignore warnings) (a new field in `--json`, so still v1, and `ok` unchanged); project customizations are never written into template files, but in a place that `jerome update` does not touch; first test: claude-watch — `jerome new` copies the template only once, so without this fixes never reach existing projects, and file dates are unreliable after git operations and copies, while hashes are not.
- D31: (superseded by D33) The CLI reaches MementoVault through its MCP endpoint over HTTP, since there is no REST API for documents: one stateless `POST` per call with `Authorization: Bearer <token>` and a JSON-RPC `tools/call`, no `initialize` and no session, passing `collection` as an argument; it calls `documents list` in the project's collection, then `documents get` on the document titled exactly "Brief", whatever its slug, and strips the `# Brief` line the tool puts before the content; errors come back as `result.isError`; URL and token live in `~/.config/jerome/mementovault.json` (`url`, the full MCP endpoint, and `token`), mode 600, never in a project; a workspace token is recommended, created only for Jérôme so it can be revoked on its own, and the CLI only lists and reads; the skill's MementoVault adapter no longer promises the `brief` slug and finds the brief by title inside the collection; refines D22 — document slugs are unique per workspace, not per collection, so a second project's brief gets `brief-2`; collection documents would have per-collection slugs but are always loaded into context, costing tokens in every claude.ai session; MementoVault tokens have no scopes or read-only mode.
- D32: Project customizations of the lead agent's behaviour (rules, conventions, preferences) live in PROJECT.md under `## Project rules`, never in CLAUDE.md or other template files; the template's CLAUDE.md says so, and the lead agent adds the section when the first rule appears; resolves Q6 (budget per project: D37) — PROJECT.md is already imported by CLAUDE.md, so no extra line in every project; it is a state file that `jerome update` never touches, and the lead agent already owns it; the rules share PROJECT.md's 800-token budget, and `jerome doctor` warns when it is exceeded.
- D33: MementoVault leaves Jérôme: no `--from-vault`, no token, no storage adapter in the skill, and no `"storage"` key in `~/.config/jerome/config.json`; a brief moves from the phone to the Mac through the claude.ai history or the clipboard, with `jerome new <name> --from-file -`; the skill saves into the project files inside a Jérôme project, and otherwise shows the brief in a markdown block to copy; the integration is parked as P3; supersedes D22 and D31, refines D15 and D26 — a token with full access to the workspace and an external service are too much for a step that the clipboard does for free.
- D34: The contract is the brief/v2 format, not the skill: `jerome prompt` prints the briefing instructions of the installed version, to paste into any chat (claude.ai, ChatGPT, Gemini…); one source for both: the briefing rules live in the skill's `references/briefing.md`, which the skill reads and `jerome prompt` concatenates with the format from `references/brief-v2.md`, leaving out what only makes sense in Claude Code (where to save, import); in a chat the brief always ends up in a single markdown block, and explicit confirmation of decisions holds there too; the skill stays in the template for briefings inside Claude Code, and uploading it to claude.ai becomes optional; refines D14 and D26 — anyone can run a briefing anywhere, and the format is the only thing the CLI has to understand.
- D35: Tolerant import with `jerome new <name> --from-file <path|->`: code fences around the text (as the chats' "copy" buttons add) are removed first; a valid brief/v2 or brief/v1 is imported by the CLI at zero tokens, and text before the front matter or between it and the first section (chats often add a sentence) is left out with a warning, so it does not send a valid brief to the model; a declared but unknown format (e.g. `brief/v3`) stops the command before anything is created and asks to update Jérôme; any other text, a brief/v2 with missing sections included, is saved as is in `brief.md` with a warning saying why it is not valid, and the CLI writes a provisional PROJECT.md whose only content is the instruction to convert `brief.md` with the project-brief skill before any other task (if the first message asks for something else, the lead agent acknowledges it in one line and starts the conversion, without answering or doing anything for it first), list the decisions found and have the user confirm them in one block before recording, then replace the provisional file; `brief.md` stays as the original text for reference; `jerome doctor` warns while PROJECT.md is still provisional; the heartbeat scheduler (phase 8) never runs on a project with a provisional PROJECT.md and opens a decision request instead; empty input is an error; `-`, the folder name and the `status: draft` warning stay as in D29; refines D29 — free text costs model tokens only once, PROJECT.md is loaded at startup so the lead agent sees the instruction without growing CLAUDE.md, and text from another chat contains the model's proposals that the user never confirmed.
- D36: PROJECT.md, loaded at every turn, holds only what the lead agent needs every turn: Goal, Constraints, Agent limits and, once it exists, `## Project rules` (D32); Context, Out of scope, Success, Tools and Pace and usage go to `scope.md`, a state file read only when needed, like decisions.md: before proposing an approach, a plan or agents, before calling work done, when a request may be out of scope, and when setting up tools or the heartbeat pace; CLAUDE.md says so by widening its decisions.md line, and its budget goes from 600 to 650 tokens; the brief/v2 format does not change, only where its sections land; `jerome update` never touches `scope.md`; `jerome doctor` warns when PROJECT.md still has sections that now belong in `scope.md`, and says how to migrate — measured on a real, carefully interviewed brief (prova-brief), PROJECT.md was 1,600 tokens, 592 of them for Success alone; a long brief is the normal case and must not be shortened, so it is split: about 630 tokens stay in every call and about 1,000 are paid only in the turns that need them.
- D37: Token budgets are warnings, never blocks, so Jérôme handles projects of any size; the defaults (CLAUDE.md 650, 680 since D49, PROJECT.md 800) can be changed per project in `.jerome` under `"budgets"` (e.g. `{ "PROJECT.md": 1200 }`), for projects that really need more context loaded every turn; `jerome update` keeps that field; no information from the brief is ever dropped to fit a budget: it moves to a file read on demand instead — budgets exist to make costs visible, not to cap what a project can be.
- D38: The MANIFEST stays in the package and is no longer copied into projects, since `jerome update` reads the installed one; `jerome update` removes a file the template no longer has when its hash matches the one recorded in `.jerome` (unchanged since it was copied), with the same confirmation as updates, and reports and keeps it when it was changed in the project or has no record; this applies to the root MANIFEST of existing projects and to any future file dropped from the template; refines D17 and D30 (which only reported dropped files) — a file the project never uses is clutter, and the recorded hash proves it is still the template's copy.
- D39: The model of an agent follows the kind of work, not a hierarchy: Opus for code and writing that stays (specifications, content), Sonnet for research and analysis, Haiku for mechanical work (counts, extractions, formatting) and the documentation agent; the lead agent runs on the model the user picks for the session; a project can change the model of a single agent only when the user asks the lead agent, which edits the agent file and records the decision; never automatically: at most the lead agent proposes a change with a decision request; refines D5 — quality where the work stays, quota saved where it doesn't, and the user always knows what each agent costs.
- D40: The agent catalog lives in the template, in the project-team skill (`.claude/skills/project-team/agents/`), listed in the MANIFEST; refines D10 — the lead agent can read it inside the project without knowing where npm installed the package, `jerome update` keeps it current, and outside `.claude/agents/` its agents cost nothing until they are created.
- D41: Every catalog agent declares `model`, only the `tools` it needs and `omitClaudeMd: true` (D27); its body holds the default limits and a `## Project limits` section, since it does not read PROJECT.md; it replies in at most 150 words in short lines, without nested lists, even when the task asks for more (outcome, files written, what the lead agent must decide), with details in the files it writes or in `notes/YYYY-MM-DD-<agent>-<topic>.md`, never in /tmp; when it changes something relevant it appends one line to `docs/_pending.md` (D25), which the read-only researcher and analyst never do; the first catalog: developer and writer (opus), researcher and analyst (sonnet), clerk and documentarist (haiku) — the lead agent's context grows by a few lines per task, and every agent's cost is declared; the limit was first "5 lines", but on claude-watch replies ran to 190–250 words, with the lead agent itself asking for 8 lines and details in /tmp, while with the final wording (confirmed by Fabio) a Sonnet review replied in 137 words with details in `notes/` and an Opus developer in 175, so the limit is still exceeded at times.
- D42: The lead agent proposes the team with the project-team skill, from scope.md and decisions.md: the smallest team that covers the work, each agent with its task, model, tools and reason, ending with a decision request; it writes `.claude/agents/` only after the user's explicit confirmation and records the team as a decision; later changes go through the same skill; files in `.claude/agents/` belong to the project: `jerome update` never touches them, even when they come from the catalog, and a MANIFEST that lists them is refused — the team is the user's choice, and template updates must not overwrite it.
- D43: `/docs` is a template skill invoked only by the user (`disable-model-invocation`, so it costs nothing per turn) that runs the documentarist on `docs/_pending.md`; `jerome docs [dir]` runs it headless as a service call: from a fixed service folder per project under `~/.cache/jerome/service/`, emptied before each call, with `--no-session-persistence`, `--settings` pointing to the project's `settings.local.json`, `--add-dir` for the project, the project's own documentarist if it has one (otherwise the catalog's) passed with `--agents`/`--agent`, and write access only to the project's `docs/`; an empty queue makes no call; `jerome doctor` warns (`docs-queue`) above 20 entries and (`agents`) about agents without a declared model or without `omitClaudeMd: true`, without changing `ok`; implements D25 — documentation at Haiku prices, without CLAUDE.md, transcripts or plugins.
- D44: The delegation rule of CLAUDE.md points to the project's agents: "Delegate to the agents in `.claude/agents/`. Create or change agents and their models only with the project-team skill, after the user confirms." It replaces the line on the cheapest model, which D39 contradicts; together with "Agents reply in at most 150 words, details in project files (`notes/`), never /tmp; don't ask for more."; CLAUDE.md is 635 tokens (budget 650, D37) — the rules on teams live in the skill, read only when needed.
- D45: When PROJECT.md's Agent limits change, the lead agent updates the `## Project limits` section of every agent in `.claude/agents/` through the project-team skill, in the same turn — with `omitClaudeMd` agents never read PROJECT.md, so a limit not copied into their file does not exist for them.
- D46: The default limits are binding, not only written: `jerome doctor` (run by `jerome new`) adds permission deny rules to the project's versioned `.claude/settings.json` for pushing (`git push`, `git -C * push`), merging and releasing on GitHub (`gh pr merge`, `gh release create`), publishing packages and images (npm, pnpm, yarn, bun, cargo, twine, uv, poetry, gem, docker push), deploying (vercel, netlify, firebase, fly, wrangler) and sending email (sendmail, mail, mailx), keeping the project's other settings and rules; `doctor --check` fails while a rule is missing; buying and email through connectors cannot be expressed as rules and rely on the written limits; Jérôme's own repository is skipped; the user can still run a denied command with `!` or in a terminal — tested on Claude Code 2.1.300: deny rules block the main session, built-in and custom subagents, headless runs, compound commands (`cd x && git push`) and env prefixes, even with `--dangerously-skip-permissions` and with `--allowedTools 'Bash(git *)'`; `git -C . push` slipped past `git push *` until its own rule was added.
- D47: Branches and merges by default: every task runs on its own branch; the lead agent merges it into main by itself when the tests pass and there are no conflicts, and reports the merge in its reply; it asks the user only when tests fail or there is a conflict; in a heartbeat the same rule applies, and the failed case becomes a decision request; subagents never merge; pushing stays forbidden (D46); the default limit becomes "no sending, publishing, deploying, pushing, purchases or emails: drafts and proposals only; tasks on branches, merged to main only by the lead agent when tests pass with no conflicts", in CLAUDE.md, in the brief format's default L1 and in the catalog agents ("never … push, merge …"); CLAUDE.md is 649 tokens after shortening two rules without changing them; existing projects keep their old L1 in PROJECT.md, which forbids merging, until the user asks the lead agent to update it (and, with D45, the agents' copies); refines D46's default limits — merging a branch with passing tests is local and reversible, asking every time slows the work for nothing, while pushing is what leaves the machine.
- D48: Besides the deny rules (D46), `jerome doctor` (run by `jerome new`) writes into the project's `.claude/settings.json` allow rules for the safe local operations: `git status`, `log`, `diff`, `show`, `rev-parse`, `merge-base`, `stash list`, `add`, `commit`, `switch`, `checkout`, `branch`, `merge` (all as `Bash(git <op> *)`) and the exact test commands `npm test`, `pnpm test`, `yarn test`, `bun test`, `node --test`, `pytest`, `cargo test`, `go test ./...`, and ask rules for the forms that discard work (`git checkout -- *`, `git checkout * -- *`, `git checkout .`, `git checkout -f *`, `git switch -f *`, `git switch --discard-changes *`, `git branch -D *`, `git commit --amend *`); `doctor --check` fails while a rule is missing, and `doctor` warns (`trust`) when the folder has not been trusted in Claude Code, which ignores project allow rules until then (deny rules apply anyway) — auto mode had blocked a merge into main as if it were a deploy, and then a `git status`; allow, ask and deny rules resolve before the auto-mode classifier, and test commands are exact because auto mode drops wildcarded package-manager and interpreter rules; tested on Claude Code 2.1.300 in a trusted throwaway repository in `dontAsk` and auto mode: every allowed command ran, the asked ones and `git push` were refused; the original block could not be reproduced headless, where auto mode let even an explicitly requested `git reset --hard` through.
- D49: The lead agent runs commands that change the repository one at a time, never chained, checking each result before the next; the rule is in CLAUDE.md, whose budget goes from 650 to 680 tokens (676 now, about +27 tokens per call); a `PreToolUse` hook in phase 6 refusing chained repo-changing commands is the second protection — the lead agent had chained commit, test, switch and merge, and when a block hit it no longer knew what had run.
- D50: A rule goes into CLAUDE.md only if the lead agent needs it at every turn; rules needed at specific moments go into a skill — CLAUDE.md is paid at every call, a skill's body only when it applies.
- D51: One database per project, `.jerome.db` at the project root (with its `-wal` and `-shm` files), kept out of git: `jerome doctor` (run by `jerome new`) creates it, migrates it and adds `.jerome.db*` to `.gitignore`; there is no global database; refines D9 — every figure the lead agent and the viewer need is per project, and nothing has to be shared between projects but the account data of D52.
- D52: Account-wide data lives in `~/.config/jerome/account.json` (or under `$XDG_CONFIG_HOME`), schema `jerome.account/v1`: the latest reading of the 5-hour and 7-day windows (`used`, `resetsAt`, `readAt`, `source`) and the global limits of D12 under `limits`; written only when a value changes, through a temporary file and a rename, by `jerome statusline` and the heartbeat runner (`rate_limit_event`); no history of the %, since the viewer and the pauses only need the latest; per-project limits (Q2) go in `.jerome` next to the budgets; revises D12, D20 and D23 — a small file is enough for one reading and two thresholds.
- D53: Schema v1 holds only what phases 6-9 need: `runs` (one row per session or run: the log line of D13), `usage` (one row per API call, keyed by `request_id`), `usage_daily` (sums of old usage), `transcript_reads` (how far each transcript has been read; a transcript shorter than its saved offset is read again from the start), `events` (hook events with numbers and names only, never contents) and `requests` (decision requests, phase 8); allowed values are CHECK constraints and model prices live in `src/models.js`, so there is no seed; a response's lines repeat the `requestId` but `output_tokens` grows until the last line, so each usage field keeps its largest value — on claude-watch 11 of 134 calls had lines with different usage, and the totals now match an independent count exactly (4,310,921 tokens); revises D10's seed.
- D54: Numbered migrations `migrations/NNN-name.sql` in the package, schema version in SQLite's `user_version`, each migration in its own transaction, applied by whoever opens the database to write (and by `jerome new` and `doctor`); a database newer than the package is never written and fails `doctor`'s `db` check; WAL, `busy_timeout` 5 s, foreign keys on; `doctor --check` reads the version from the file header, since even a read-only connection creates the `-shm` file; `bin/jerome.js` drops only node:sqlite's ExperimentalWarning, still printed by Node 24.13.
