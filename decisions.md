# Decisions

- D1: One project = one folder with the template repo cloned into it — projects are self-contained and easy to start. (refined by D17)
- D2: The user talks to the lead agent in plain Claude Code (terminal or VS Code), with no CLI/TUI of its own — don't duplicate what Claude Code already does well.
- D3: Subagents, not Agent Teams — Teams use several times as many tokens.
- D4: The lead agent passes file paths to subagents, not contents; subagents return a short summary and write the details to files — the lead agent's context grows slowly.
- D5: One model per agent: the large model only for the lead agent, Sonnet/Haiku for research and repetitive work — saves quota.
- D6: Heartbeat: a scheduler launches headless `claude -p` with preconfigured permissions, an overlap lock and a budget per run — autonomous background work.
- D7: Narrative state in short markdown files (PROJECT.md, decisions.md, open.md), updated only by the lead agent — no conflicts, and sessions resume without rereading everything.
- D8: SQLite for events, logs and usage, written by hooks and scripts; the model queries it through bash scripts, not MCP — zero tokens to write, no fixed tool overhead.
- D9: The .db file is not versioned: numbered SQL migrations in the repo, DB created at setup, WAL mode — no binaries in git, updates without data loss.
- D10: Seed only for reference data (states, event types, default budgets, model table); agent templates as markdown in templates/agents/ — agents and goals come from the briefing, not from rigid structures.
- D11: Local read-only viewer, separate from execution: agent structure, messages, logs, reports, tokens, cost and estimated subscription % — if it breaks, the agents keep working.
- D12: Limits at two levels, per project and global (global DB in ~/.config/jerome/) — the subscription is one and shared across projects.
- D13: Reporting: one log line per run, a periodic digest from the lead agent, a "decision request" when Fabio is needed — always know what was done.
- D14: Briefs in brief/v1 format with the project-brief skill; the source of truth is in the repo (.claude/skills/), with a copy uploaded to claude.ai — one briefing method everywhere. (refined by D26; by D34: the copy on claude.ai is optional)
- D15: (refined by D33: from the phone through the clipboard and `--from-file -`) Starting from the phone: brief saved in MementoVault and imported on the PC; starting from the PC: briefing in Claude Code with files written right away — starting from the phone is the typical case.
- D16: (superseded, see D18) The tool is called Odino; project marker `.odino` at the root — Fabio's choice, resolves Q1.
- D17: The template content lives in `template/` and the "new project" command copies only that folder; the project-brief skill has its canonical copy in `template/.claude/skills/`, linked from the root for development; project updates touch only the files listed in the manifest — Jérôme's development files never end up in projects, and updates never touch project state.
- D18: The tool is called Jérôme; `jerome` (lowercase, no accents) for the command, package, `.jerome` marker and paths — a French nod to Claude; Saint Jerome is the patron saint of translators, like the lead agent translating Fabio's ideas into tasks.
- D19: CLI as a Node package with the commands `jerome new`, `jerome view`, `jerome hook <event>`, installable with `npm i -g github:meltinbitfarm/jerome`; project hooks call the CLI instead of copied scripts; SQLite through the built-in `node:sqlite`, no native dependencies (requires Node ≥ 24, verified on 24.13.0); the package name is `@meltinbitfarm/jerome`, in package.json from now on and on npm if it is ever published (updated: meltinbitfarm scope and repo) — updating the package updates the hooks of every project without recopying scripts, and installing compiles nothing (V2).
- D20: Source of usage data: tokens per agent and per run read from Claude Code's JSONL transcripts, with hooks as the trigger (`agent_transcript_path` / `transcript_path`), lines deduplicated by `requestId` and cost estimated from the seed's model table; heartbeats run with `--output-format stream-json` and store the usage of the subscription windows (5 hours and 7 days) from the `rate_limit_event` in the global DB; global limits are expressed as % of these windows — hooks carry no tokens, and the only real subscription % is the one Claude Code exposes (see notes/usage-probe.md).
- D21: Lean project profile: `jerome new` writes into the project's `.claude/settings.local.json`, which it adds to `.gitignore`, the keys that turn off installed plugins, synced ones included (`enabledPlugins` set to false), claude.ai connectors (`disableClaudeAiConnectors`), bundled skills (`disableBundledSkills`) and skills synced from claude.ai (`skillOverrides` set to "off", including the synced copy of project-brief: the project copy stays on, canonical per D14); any MCP server needed is added only in the project's `.mcp.json`; the profile names the plugins and skills installed on the machine, so it never goes in the versioned `.claude/settings.json`, where only machine-independent settings belong; the CLI manages only its own keys and leaves the others alone; `jerome doctor` moves profile entries it finds in `settings.json` to the local file, and rechecks the profile against what is installed and fixes it, including before every heartbeat; if it cannot, the heartbeat does not start, the block is logged and a "decision request" is opened (D13) — fixed startup cost goes from ~29k to ~12k tokens (notes/usage-probe.md §6), and the plugin list depends on the machine, so it has to be generated, not copied from the template. (updated: local settings instead of settings.json)
- D22: (superseded by D33) The import from MementoVault is done by the CLI with `jerome new <name> --from-vault <slug>`, without the model: it downloads the collection's `brief` document, checks `format: brief/v1` and sorts the sections into PROJECT.md, decisions.md and open.md following the "Import" table of brief-v1; it uses MementoVault's REST endpoint if one exists for reading a document, otherwise it calls the MCP endpoint directly over HTTP; the token lives in `~/.config/jerome/` (mode 600), never in the project; refines D15, and creating the three files initially does not conflict with D7 — import at zero model tokens, and no Memento MCP in the lean profile. (refined by D26: brief/v2, brief/v1 still accepted; refined by D31: MCP over HTTP, brief found by title)
- D23: The project status line calls `jerome statusline`, which writes the % of the 5-hour and 7-day windows to the global DB only when it changes from the last reading; it does not replace the personal status line: if one is configured, it calls it with the same input and appends its own part; it is the second source of the %, next to the heartbeats' `rate_limit_event` (D20) — interactive sessions update the % too, with no duplicate rows and without losing Fabio's status line.
- D24: Everything versioned in Jérôme's repo is in English: documentation (README.md and docs/), CLI messages, code comments and the development files (decisions.md, open.md, PLAN.md, PROJECT.md, notes/), as well as commit messages; the only exception is brief.md, which stays in Italian as a snapshot of the starting point, with an English line at the top explaining it; Fabio keeps writing in Italian, and the agent records in English; updating the documentation is part of the definition of "done" for every phase, closed ones included — the repo is public, anyone who finds it understands what it does and how to use it, and the documentation never falls behind the code. (updated: development files, comments and commits in English too)
- D25: In projects, every subagent that changes something relevant appends one line to `docs/_pending.md` (date, agent, files touched, what changed in one sentence); a documentation agent on a cheap model (Haiku, D5) integrates it into the documentation, only on command: `/docs` in a session, `jerome docs` headless; integrated lines leave the queue; `jerome doctor` warns, without blocking, when the queue exceeds 20 lines — documentation gets updated without spending tokens on every task, and nothing gets lost in the meantime.
- D26: The project-brief skill is generic: instructions in English, and the briefing is held in the language the user writes in; brief format brief/v2 with fixed English section headings and IDs (Goal, Context, Constraints, Decisions…) and content in the user's language, while import still accepts brief/v1 with the Italian headings; storage is optional: inside a Jérôme project the project files, always; an external store when available, with MementoVault as the first adapter, described in a separate reference file loaded only when needed; otherwise the brief is shown as markdown to copy; no references to a specific person — anyone can use the template and the skill, the CLI can parse every brief without translating, and nobody pays tokens for a store they don't use. (refined by D33: no stores; D34: rules in `references/briefing.md`, shared with `jerome prompt`)
- D27: The agents in the template catalog (templates/agents/) declare `omitClaudeMd: true`, so they run as subagents without CLAUDE.md and the PROJECT.md it imports; built-in subagents still load CLAUDE.md, which tells them to ignore it — measured on a test project, a subagent call costs 2,518 input tokens with CLAUDE.md and 1,142 without, and those instructions are meant for the lead agent anyway.
- D28: `jerome doctor --json` is Jérôme's stable interface for external tools, such as claude-watch: one JSON object on standard output and nothing else, with `schema` (today `jerome.doctor/v1`), `ok`, `jerome` (CLI version), `mode`, `project`, `checks`, `profile`, `context` and `warnings`; the exit code always matches `ok` (0 true, 1 false, 2 wrong usage with nothing on standard output), and warnings never make `ok` false; check `id`s are stable, while `label` and `detail` are for humans; adding fields keeps v1, while renaming or removing a field, or changing its meaning, bumps the version; the human output can change freely; `--check` verifies and reports without writing anything, needed fixes go to `profile.pending` and make `ok` false, and external tools must call `jerome doctor --check --json` — they get a contract that does not break silently, instead of parsing the human output or Claude Code's `/context`, and checking a project never changes it.
- D29: Besides `--from-vault`, `jerome new <name> --from-file <path>` imports a brief from a file, and `-` reads it from standard input (so `pbpaste | jerome new <name> --from-file -` works); same validation and same mapping as `--from-vault`, done by the CLI without the model; the two options exclude each other; the folder name is the one given to `jerome new`, while the brief's `name` becomes the title in PROJECT.md; a brief with `status: draft` is imported with a warning; any `format` other than brief/v2 or brief/v1 stops the command before anything is created — with D26 the store is optional, and for anyone not using one this is the only way to bring a brief made on claude.ai into a project. (refined by D33: `--from-vault` is gone; D35: free text is accepted)
- D30: `jerome update [dir]` brings the template files of an existing project up to the installed version: it touches only the paths listed in the MANIFEST and never the state files (PROJECT.md, decisions.md, open.md, archive.md, brief.md, `.jerome`, `.claude/settings.local.json`), refusing them even if a MANIFEST listed them; it shows a diff per file and asks for confirmation before writing, `--check` shows the diff and writes nothing, `--yes` skips the question; `.jerome` becomes a JSON file with a schema version field, the Jérôme version and a hash of every template file as copied; a file whose hash matches the recorded one is updated, a file changed in the project is overwritten only after its own confirmation, and in projects created before this decision (empty `.jerome`) every file that differs from the template counts as changed in the project; paths dropped from the MANIFEST are reported, never deleted; `jerome doctor` adds a warning, not a failing check, when the template files differ from the installed version (skipped in Jérôme's own repository, where `template/` is the source and `jerome update` refuses to run, since an always-expected warning teaches to ignore warnings) (a new field in `--json`, so still v1, and `ok` unchanged); project customizations are never written into template files, but in a place that `jerome update` does not touch; first test: claude-watch — `jerome new` copies the template only once, so without this fixes never reach existing projects, and file dates are unreliable after git operations and copies, while hashes are not.
- D31: (superseded by D33) The CLI reaches MementoVault through its MCP endpoint over HTTP, since there is no REST API for documents: one stateless `POST` per call with `Authorization: Bearer <token>` and a JSON-RPC `tools/call`, no `initialize` and no session, passing `collection` as an argument; it calls `documents list` in the project's collection, then `documents get` on the document titled exactly "Brief", whatever its slug, and strips the `# Brief` line the tool puts before the content; errors come back as `result.isError`; URL and token live in `~/.config/jerome/mementovault.json` (`url`, the full MCP endpoint, and `token`), mode 600, never in a project; a workspace token is recommended, created only for Jérôme so it can be revoked on its own, and the CLI only lists and reads; the skill's MementoVault adapter no longer promises the `brief` slug and finds the brief by title inside the collection; refines D22 — document slugs are unique per workspace, not per collection, so a second project's brief gets `brief-2`; collection documents would have per-collection slugs but are always loaded into context, costing tokens in every claude.ai session; MementoVault tokens have no scopes or read-only mode.
- D32: Project customizations of the lead agent's behaviour (rules, conventions, preferences) live in PROJECT.md under `## Project rules`, never in CLAUDE.md or other template files; the template's CLAUDE.md says so, and the lead agent adds the section when the first rule appears; resolves Q6 — PROJECT.md is already imported by CLAUDE.md, so no extra line in every project; it is a state file that `jerome update` never touches, and the lead agent already owns it; the rules share PROJECT.md's 800-token budget, and `jerome doctor` warns when it is exceeded.
- D33: MementoVault leaves Jérôme: no `--from-vault`, no token, no storage adapter in the skill, and no `"storage"` key in `~/.config/jerome/config.json`; a brief moves from the phone to the Mac through the claude.ai history or the clipboard, with `jerome new <name> --from-file -`; the skill saves into the project files inside a Jérôme project, and otherwise shows the brief in a markdown block to copy; the integration is parked as P3; supersedes D22 and D31, refines D15 and D26 — a token with full access to the workspace and an external service are too much for a step that the clipboard does for free.
- D34: The contract is the brief/v2 format, not the skill: `jerome prompt` prints the briefing instructions of the installed version, to paste into any chat (claude.ai, ChatGPT, Gemini…); one source for both: the briefing rules live in the skill's `references/briefing.md`, which the skill reads and `jerome prompt` concatenates with the format from `references/brief-v2.md`, leaving out what only makes sense in Claude Code (where to save, import); in a chat the brief always ends up in a single markdown block, and explicit confirmation of decisions holds there too; the skill stays in the template for briefings inside Claude Code, and uploading it to claude.ai becomes optional; refines D14 and D26 — anyone can run a briefing anywhere, and the format is the only thing the CLI has to understand.
- D35: Tolerant import with `jerome new <name> --from-file <path|->`: code fences around the text (as the chats' "copy" buttons add) are removed first; a valid brief/v2 or brief/v1 is imported by the CLI at zero tokens, and text before the front matter or between it and the first section (chats often add a sentence) is left out with a warning, so it does not send a valid brief to the model; a declared but unknown format (e.g. `brief/v3`) stops the command before anything is created and asks to update Jérôme; any other text, a brief/v2 with missing sections included, is saved as is in `brief.md` with a warning saying why it is not valid, and the CLI writes a provisional PROJECT.md whose only content is the instruction to convert `brief.md` with the project-brief skill before any other task, list the decisions found and have the user confirm them in one block before recording, then replace the provisional file; `brief.md` stays as the original text for reference; `jerome doctor` warns while PROJECT.md is still provisional; the heartbeat scheduler (phase 8) never runs on a project with a provisional PROJECT.md and opens a decision request instead; empty input is an error; `-`, the folder name and the `status: draft` warning stay as in D29; refines D29 — free text costs model tokens only once, PROJECT.md is loaded at startup so the lead agent sees the instruction without growing CLAUDE.md, and text from another chat contains the model's proposals that the user never confirmed.
